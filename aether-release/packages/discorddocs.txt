discord.ind - Indent Discord Module Docs
========================================

Overview
--------
discord.ind gives you a native Discord API surface for Indent scripts.
It currently supports:
- Bot token auth and session checks
- A persistent gateway runner for staying online
- Prefix command registration and automatic MESSAGE_CREATE handling
- Channel message send/edit/delete
- Button/component message builders and send helpers
- DM send flow
- Reactions and typing
- Slash command registration and interaction replies
- Gateway websocket connect/identify/recv/heartbeat/close helpers
- Gateway polling with timeout, reconnect backoff, and ready-state tracking
- Event packet parsing helpers
- Extended REST helpers for guild/member/role/channel moderation and command management
- Thread, emoji, invite, and scheduled-event helpers
- Interaction deferral/original response edit/delete helpers

Important implementation note
-----------------------------
discord.ind is a script-oriented native toolkit.
It covers practical bot operations while keeping loop scheduling and reconnect
policy explicit in your script. Use `Run`/`Start` (or `RunActive`) to keep a
live gateway connection open after setup; `UseToken` only stores the active
session and does not block by itself.

For the most ergonomic setup, prefer `UseToken` + `Add*CommandActive` +
`RunSimpleActive`. That path is intentionally minimal and keeps command
registration plus runtime dispatch in one straightforward flow.

The current command/gateway design is a clean-room Indent implementation
inspired by discord.py architecture (Client/Bot setup, intents resolution,
dispatch-style message processing, and reconnect behavior). Imported module
helpers now compose reliably inside `discord.ind`, so the simplified helper
paths below are safe to use in normal scripts.

Quick start
-----------
Simplest flow (set token once, then use natural commands):

UseToken;
	"YOUR_BOT_TOKEN"

	dynamic

		"YOUR_CHANNEL_ID"
		"Hello from Indent"

	"YOUR_BOT_TOKEN"
RunActive

Very simple, very functional bot mode (recommended)
---------------------------------------------------
Use this when you want minimal syntax, command args, and action commands
without ceremony.

Newest easy-mode helpers (lowest ceremony)
- `QuickBot(token, prefix)` to create + activate a bot in one call.
- `QuickBotWithStatus(token, prefix, status, watching)` to create, activate,
  and set normalized presence immediately.
- `UseEnvToken(envName, fallback)` to bootstrap token from env with fallback.
- `SetupSimpleActive(...)` and `SetupSimpleActiveWithModeration(...)` to
	configure active session + commands in one call.
- `AddReply`/`AddReplyActive` as friendlier aliases for text commands.
- `AddReplies`/`AddRepliesActive` to register many text commands in one call.
- `ActionCreateTextChannel`, `ActionDeleteChannel`, `ActionBanMember`,
  `ActionApiPost` to build action payloads without manual dictionaries.
- `AddModerationPackActive(guildId)` to preload `mkchan`, `rmchan`, and `ban`.
- `Say`, `SayEmbed`, `SayButtons`, `DMUser`, `React`, `Unreact`, `Typing`,
	`FetchChannelActive`, and `FetchMessageActive` for active-session convenience.

Startup troubleshooting for Angela/simple bots
---------------------------------------------
- If token is still `YOUR_BOT_TOKEN`, `RunActive`/`RunSimpleActive` now fail fast with a clear flag message.
- If Discord returns 401 on gateway startup, confirm bot token is valid and bot is invited to your server.
- If bot connects but command replies do not fire, ensure Message Content intent is enabled in Discord Developer Portal.
- Use `SetStatusActive` and one of the `Set*ActivityActive` helpers before `RunSimpleActive`.

Text command arguments (simple placeholders)
-------------------------------------------
`AddTextCommand` also supports message arguments using `{0}`, `{1}`, ...
placeholders in the response string.

Example:

def.var: withKickText
	dynamic
	AddTextCommand;
		ready
		"kick"
		"kick; {0}"

Then in Discord:
- `!kick user123` returns `kick; user123`

Action commands (same simple style, but with complex behavior)
--------------------------------------------------------------
Use AddActionCommand when you want the same command declaration pattern,
but the output is an operation instead of plain text.

Get: AddActionCommand From: discord

def.var: withAction
	dynamic
	AddActionCommand;
		ready
		"mkchan"
		{"type": "create_text_channel", "guild_id": "YOUR_GUILD_ID", "topic": "Created by Indent command", "ack": "Creating channel..."}

Run;
	withAction

Then in Discord:
- `!mkchan raids` creates a new text channel named `raids`

Supported built-in action types:
- `create_text_channel`
- `delete_channel`
- `create_role`
- `ban_member`
- `api_post` (generic REST escape hatch)

Action values can use either fixed fields in the action object or command
arguments from the message content.

Persistent live session pattern
-------------------------------
`UseToken` prepares the active session object.
`RunActive` keeps the bot online by opening the gateway, identifying, and
continuing to heartbeat on the gateway loop.

`RunSimpleActive` is the streamlined runner that keeps this same behavior but
executes command parsing/dispatch in one place for the active-session command
APIs (`AddTextCommandActive` / `AddActionCommandActive`).

Use this when you want the Indent script to keep a long-lived live session.

Why `def.var` and `dynamic` exist
---------------------------------
- `def.var` is the variable declaration statement in Indent. It does define the variable.
- `dynamic` means "let this value be any runtime type" (dictionary/list/string/etc).
- In Discord helpers, many returns are JSON-like dictionaries, so `dynamic` is the natural type.
- `UseToken` gives you the session-based flow; `Send`, `SendEmbed`, and `DM` reuse that session, while `SendWith`, `SendEmbedWith`, and `DMWith` accept explicit token/bot values.

Current native limitations
--------------------------
- Full async framework orchestration is still script-managed.
- Event-dispatch/cache abstractions are lighter than full framework models.
- Gateway reconnect strategy remains explicit in user scripts.

Gateway starter example
-----------------------
Get: Login From: discord
Get: GatewayInfo From: discord
Get: GatewayOpen From: discord
Get: GatewayIdentify From: discord
Get: GatewayRecv From: discord
Get: GatewayHeartbeat From: discord
Get: GatewayClose From: discord
Get: IntentsMessageContentValue From: discord
Get: ParseGatewayOpcode From: discord
Get: ParseGatewayData From: discord
Get: IsSuccess From: discord
Get: BodyText From: discord

def.var: session
	dynamic
	Login;
		"YOUR_BOT_TOKEN"

def.var: me
	dynamic
	session

def.var: info
	dynamic
	GatewayInfo;
		me

def.var: infoOk
	dynamic
	IsSuccess;
		info

if infoOk:
	def.var: infoBody
		dynamic
		BodyText;
			info

	def.var: details
		dynamic
		json_loads;
			infoBody

	def.var: opened
		dynamic
		GatewayOpen;
			details["url"]

	if opened["ok"]:
		def.var: sid
			int
			opened["socket_id"]

		GatewayIdentify;
			sid
			me["token"]
			IntentsMessageContentValue

		def.var: first
			dynamic
			GatewayRecv;
				sid

		if first["ok"]:
			def.var: op
				int
				ParseGatewayOpcode;
					first
			say: "first op=" + op
			if op == 10:
				def.var: helloData
					dynamic
					ParseGatewayData;
						first
				GatewayHeartbeat;
					sid
					0

		GatewayClose;
			sid

Troubleshooting
---------------
1) Publish fails with clone error
	- Ensure registry is main branch:
	  air registry github rafih110610/indent-air main index.txt

2) 401 / 403 from Discord
	- Token invalid or bot missing permission in guild/channel.

3) 404 on message/channel routes
	- Channel ID or message ID wrong, or bot cannot access it.

4) Gateway closes quickly
	- You must heartbeat using the hello interval and keep processing recv packets.
